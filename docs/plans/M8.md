## A. API

1. **Two-phase submitted text, with its own content id.** Extension submissions are unverified
   client text, so they get their own id and can never satisfy the fetch path's cache lookup.
   **[amended]** The id is `url_hash("ext:" + normalize_url(url) + "\n" + sha256(the redacted,
   cleaned paragraphs joined by "\n"))`: two readers whose extractions are identical share one
   doc and one analysis; a reader whose text differs (a subscriber's full text vs a teaser, or
   planted text) gets their own. So nobody is served text they didn't submit themselves, and a
   reader can't plant text for a real URL that others are served (paste-a-link, "Open here",
   For you and POST /v1/content {url} keep fetching through safe_fetch under `url_hash(url)`).
   The extension may reuse an already-fetched doc for the same URL: the endpoint first checks the
   fetch id (stored or pending) and returns it if present. `SubmittedRequest` gains
   `defer: bool = False`. With `defer: true`, POST /v1/content stores the redacted paragraphs as a
   `pending_contents/` doc (source `extension`) and returns `{content_id, status: "analysing",
   pii_found_before_backstop: n}` at once (the synchronous path returns
   `pii_found_before_backstop` too); the extension then calls the existing POST
   /v1/content/{id}/analyse (lease, timeout, attempts as in M6). Without `defer`, behaviour is
   unchanged. Same ingest caps (20/day; 3/day per anonymous uid, 30 shared), pending/known ids
   free (known = the fetch id or the `ext:` id, stored or pending), growth slots reserved as
   today.
   **[amended]** Both paths call `ReaderRepo.add_ingested(uid, content_id, at)` for the id they
   return, before returning, in every case: new `ext:` doc, existing `ext:` doc or pending doc
   (returns `"analysing"` if still pending), or the fetch-id doc (harmless: corpus docs are never
   hidden; a `user_ingested` fetch doc becomes visible to this reader, same as their own "Open
   here" would). The server stores the normalised URL (today `_store_pending` stores the raw one).
2. **Redaction format and false positives first.** **[amended]** Carried over from 2f037a1:
   - `app/privacy/redact.py` emits `[REDACTED:email|phone|card|aadhaar|pan]` (DESIGN §11.3) with
     shaped patterns (phone: country code, 10-digit Indian mobile with optional 0, or bracketed
     area code; Aadhaar: 4-4-4 with spaces, first digit 2–9; card: Luhn, 13–19 digits grouped
     4-4-4-x or ungrouped) and `count_redactions(text)`. Cases live in
     `apps/api/tests/fixtures/redaction.json` (7 redact cases, 10 must-stay-unchanged news lines:
     ISO dates, year ranges, large figures, Sensex/GDP numbers, wire datelines, a Luhn-invalid
     card), loaded by `tests/test_redact.py` **and** by the `redact.ts` vitest.
   - **[amended] Reader-typed text keeps its broad catch.** The shaped patterns would stop
     redacting "415-555-0132" or "020 7946 0958" in typed text that goes to embeddings or
     `link_confirm` (decision 42's privacy rule). `redact(text, typed=True)` applies the shaped
     patterns and then the old broad phone/digit-run catch (8+ digits with separators). Used by
     `profile_edit.py`, `goals.py` and `onboarding_flow.py`; article text uses the strict default.
     pytests: both strings in typed mode; the news fixture unchanged in strict mode. Placeholder
     assertions move to the new format in `test_profile_edit` and `test_onboarding_flow`
     (`test_goals` already expects it). No prompt or eval case references the old placeholders.
   - Offline check over a local copy of the stored corpus paragraphs (read-only export): number
     of paragraphs either redactor (strict mode) changes, each listed; target 0 outside real
     contact data (acceptance 5).
3. **Server-side PII backstop** on the submitted path only (`app/privacy/pii.py`), **[amended]**
   on both the deferred and synchronous paths, **before** anything is written to
   `pending_contents/`:
   - Presidio `AnalyzerEngine` with the spaCy model already in the image (`en_core_web_sm`, via
     `NlpEngineProvider`), entities EMAIL_ADDRESS, PHONE_NUMBER, CREDIT_CARD, IBAN_CODE, plus
     custom regex recognizers for Aadhaar and PAN. Lazy import (ingestion path only, like
     trafilatura), so read paths and cold start are unchanged.
   - Evidence before the number: refuse/pass fixtures (a contact page, a donor list, 5 normal
     news articles) are committed first and never changed afterwards (decision 26); then
     `pii.py` runs offline over the whole stored corpus and the finding rate per 1,000 words is
     reported. A finding counts at Presidio score ≥ a stated minimum (chosen from the same run,
     recorded with it). The threshold is set above the corpus maximum with margin; **acceptance:
     0 corpus articles refused**. Above it: 422 `personal_data` "This page looks like it holds
     personal information, so ReadLayer won't read it." (quota refunded). Below it, `redact()`
     runs on every paragraph before storing.
   - Offline and cheap: `tldextract` (a Presidio dependency) is configured with its bundled
     snapshot and no suffix-list URLs; a pytest builds the analyzer with sockets blocked. The
     time and memory to build `AnalyzerEngine` with `en_core_web_sm` are measured and stated
     against Cloud Run's 1 GiB (built once per instance, lazily); logs carry finding counts per
     entity type only, never matched text.
   - `presidio-analyzer` (pinned) added to the API; no new model download.
4. **CORS:** `CORS_ORIGINS` adds the extension origin `chrome-extension://<id>`. The id is
   stable because the manifest carries a public `key` (generated once; the private key is not
   needed for unpacked loading and is not kept). The extension's background worker is the only
   caller; content scripts never call the API.
5. **Extension pages stay private.** **[amended]** NOT_CORPUS (already on main) gains its last
   three users: `scorer.explainer_index`, `build_concepts.select_corpus`, `eval_heldout` (with a
   pytest each using an `extension` doc). **[amended] Read access:** a `source == "extension"`
   doc, or its pending doc, is served only to readers whose `ingested` holds its id: GET
   /v1/content/{id}, GET …/annotations, POST /v1/explain (span and paragraph; content id in the
   body), GET …/recommendations, POST …/analyse and PUT /v1/me/saved/{id} return 404 for anyone
   else (the same 404 as an unknown id). This re-decides "reachable
   by id" (DESIGN §17.4) for extension text only, because it can be a subscriber's paywalled
   text and its URL-derived id is guessable once the repo is public (Oct 17); `user_ingested`
   docs (fetched by the server) stay reachable by id. pytest per route.
6. **[amended] Onboarding gate (server backstop).** POST /v1/content with a *submitted* body
   from a non-anonymous caller whose onboarding isn't done → 409 `onboarding_required` (no quota
   reserved, nothing stored). One profile read, on this path only. Demo readers never gated; URL
   bodies unchanged. Existing submitted-path tests (`test_content_api`, `test_two_phase`) get an
   onboarded Google fixture.
7. No new Firestore collection; no LLM on the annotations path.

## B. [amended] Annotator 0.8.0

Additive; the web app is unaffected:
- `styles?: "inject" | "external"` on `AnnotatorOptions` **and** `PrereadOptions` (default
  `"inject"`, today's behaviour). `"external"`: the host applied the CSS; no `<style>` element is
  created. With it, the extension leaves no inline style on a strict-CSP page (which would also
  send CSP violation reports to the publisher). vitest for both entry points; default unchanged.
- Export `ANNOTATOR_CSS`. The worker applies it with `chrome.scripting.insertCSS` (activeTab),
  which a publisher's CSP can't block, together with a small extension token sheet
  (`apps/extension/src/tokens.css`): the Gloss `--rl-*` tokens, light by default and dark under
  `@media (prefers-color-scheme: dark)`, scoped to the annotator's own elements (marks inherit
  the page's text colour; cards, chips, markers and the pre-read use the tokens). The worker
  inserts both once per tab per page load (a repeat click finds the overlay and reopens nothing;
  guarded by a `data-rl-mounted` check in the content script before `insertCSS`).
- If the 3-site harness shows publisher CSS bleeding into the card (button or paragraph
  resets), scoped resets go into `ANNOTATOR_CSS` under `.rl-card`, re-checked on the web reader.
- `ANNOTATOR_VERSION` and `package.json` → 0.8.0.

## C. Extension (`apps/extension`)

1. **Manifest (MV3):** permissions `activeTab`, `scripting`, `storage`; **no** `host_permissions`,
   **no** `content_scripts`; `externally_connectable.matches` = the two Hosting origins (+
   `http://localhost:5173/*` in the dev build only); `action` with a popup; public `key`.
2. **Background service worker (`background.ts`):**
   - `chrome.action` opens the popup; the popup's "Read this page" (and a keyboard shortcut,
     `_execute_action`) triggers `readActiveTab(tabId)`.
   - **[amended]** Before injecting anything, for a Google reader: GET /v1/me/profile; if
     `onboarding.done` is false, nothing is injected and the popup shows "Finish setting up
     ReadLayer first" with a button opening the web app's `/connect` (which goes through
     `/welcome` and comes back, D). Re-checked on every click while false. Demo readers skip it.
   - Inserts the CSS (B), then injects `content.js` with `chrome.scripting.executeScript`
     (activeTab grants the current tab only), receives `{url, title, paragraphs}` or
     `{refused: reason}`.
   - All API calls (content, analyse, content detail, annotations, explain, events, graph
     answers, settings) go through the worker with the bearer token; demo readers' calls carry
     `?persona=`; the content script talks to the worker with `chrome.runtime` messages.
   - Tokens: `idToken` + `refreshToken` + expiry in `chrome.storage.session` only (cleared when
     the browser closes; never `storage.local`), left at its default `TRUSTED_CONTEXTS` access
     level (test: a content script can't read it). Refresh via Firebase's securetoken REST
     endpoint (the Auth emulator's in the dev build), not through the web app: **a deviation from
     DESIGN §11.1 ("refresh via web app")**, recorded in STATUS §4 and DESIGN §11.1 at Ship. The
     reason: the reader shouldn't need a ReadLayer tab open for the extension to keep working.
     `onMessageExternal` re-checks `sender.origin` against the allowed origins. Before deploy, the
     Firebase web API key's restrictions are checked to allow calls from the extension origin.
     Never logged.
3. **Content script (`content.ts`, IIFE bundle, injected on click only):**
   - **Refusals (before reading anything):** any `input[type=password]`, any
     `autocomplete^="cc-"` input, URL patterns for mail (mail.google.com, outlook.live.com,
     outlook.office.com, mail.yahoo.com, proton.me), banking (`/bank|netbanking|ibanking/`
     in host, known bank domains list), intranet (non-public TLDs `.local`, `.internal`, `.corp`,
     `.lan`, localhost and private IPs) and `chrome://`/file URLs. Refusal shows a quiet toast.
   - **Extraction:** `@mozilla/readability` (pinned) on `document.cloneNode(true)`; paragraphs
     from the extracted HTML's block text (`p`, `li`, `blockquote`, headings excluded), min
     length as the API's `clean_paragraphs`; title from Readability. Never raw HTML, comments
     or form fields. The URL is sent without its fragment, and `redact.ts` runs over query
     parameter values (they can carry emails or session tokens); vitest.
   - **Client redaction** (`redact.ts`, same strict patterns as `app/privacy/redact.py`, Luhn for
     card runs): emails, phones, card-like digit runs, Aadhaar, PAN → `[REDACTED:type]`. The API
     receives redacted text only; the vitest loads the shared fixture file (A2).
   - **Mounting:** the content script keeps (live element, redacted text) pairs from extraction.
     The server's paragraphs (after its own redaction and `clean_paragraphs`) map to live elements
     by **equality with the client's redacted, whitespace-normalised text**, not by index or raw
     text; **[amended]** when the endpoint returned the fetch-id doc (trafilatura's paragraphs,
     not ours), unmatched server paragraphs fall back to a normalised exact-then-prefix match
     against the live block elements; still unmatched → no notes there. It tags them
     `data-rl-paragraph="pN"`; the article text is never changed. Spans whose anchors don't
     resolve (e.g. next to a placeholder) are skipped silently (DESIGN §9). vitest with a
     paragraph containing an email, and one for the fetch-doc fallback. Mounts
     `createAnnotator(articleRoot, { styles: "external", actions: "full", onEvent, onAnswer,
     loadExplanation })` **[amended: no `loadShifted`, no `sidenote`: popover and bottom sheet]**
     on the common ancestor of the tagged paragraphs; spans, markers, the "Know this?" chip,
     dwell/text-search signals, explanations (via the worker) and the pre-read card
     (`renderPreread(..., { styles: "external" })`, inserted before the first tagged paragraph as
     `data-rl-ui`) all reuse the annotator.
   - Two-phase: "Reading this page…" toast while phase 1 runs, the overlay appears when the
     analysis finishes (poll analyse with the 202 retry, up to 180 s), "Notes are ready" toast.
     **[amended]** Errors (cap reached, `personal_data`, `onboarding_required`, 410, timeout) show
     the API's message in the toast.
4. **Popup (`popup.html/ts`):** sign-in state (Google name, or "Demo · <persona>"), "Read this
   page", persona picker for demo readers, density (minimal / balanced / guided; **[amended]**
   PATCH /v1/me/settings), "Open your reading profile" link, "Connect" link when signed out,
   **[amended]** "Finish setting up" state. Keyboard and screen-reader usable; **[amended]** light
   and dark follow `prefers-color-scheme` with the Gloss tokens.
5. **Build:** two Vite builds (ES for worker/popup, IIFE for the content script), env-driven
   API base and Firebase web key (`make extension-config` writes `.env` from the web config),
   `pnpm --filter extension build` → `dist/` ready for "Load unpacked". A build check fails if
   the manifest gains host permissions or content scripts.

## D. Web: "Connect extension"

`/connect` page (signed-in or demo): explains what the extension can see; "Connect" sends
`{idToken, refreshToken, expiresAt, persona?}` to the extension id via
`chrome.runtime.sendMessage` (only works from the allowed origins); shows connected / not
installed states. Demo readers connect as their demo session (same anonymous uid).
**[amended]** `/connect` sits under the existing onboarding gate. When the gate redirects a
signed-in, unfinished reader to `/welcome`, `App.tsx` remembers the path (returnable routes gain
`connect`), so finishing onboarding lands back on `/connect`; signed-out visits come back after
sign-in the same way. Lazy-loaded like Welcome and Privacy (main bundle stays ≤ 150 KB gzip).
Linked from the profile page. vitest: gate redirect remembers `/connect`; finish returns there.

## Data rights, privacy, cost

- No new user collection. Extension-ingested content is shared content (`contents/`,
  `pending_contents/`, source `extension`), no uid stored with it; **[amended]** the submitter's
  link to it is the existing `ingested` list (export and delete since M7.5), which also gates
  reading it (A5). Events/explanations/answers/corrections go to the existing user-data paths.
- Only redacted article text and the fragment-less, query-redacted URL leave the browser; never
  URLs of refused pages, form fields or raw HTML. The token never reaches the page or the content
  script.
- Anonymous cost: unchanged caps (3 new pages per uid per day, 30 shared; explain caps).
- Presidio runs only on extension submissions (CPU, no per-call cost).
