# M9 part 1: growth slots taken when used, and pages that missed growth grow on reopen

Branch `m9` from `main` at 0fbc3a9. Part 2 (the four M2.2 quality items) and part 3 (evals,
hardening, demo) get their own plan sections after part 1 merges.

## Context (STATUS §5, High and Medium rows; production logs 2026-10-13)
- Each new article reserves `GROWTH_PER_ARTICLE` (5) slots **in phase 1, before the fetch**, in
  three routes (POST /v1/content URL path, extension text, POST /v1/recs/open) and in
  `open_media`. The pending doc stores them (`grow_slots`) but holds no uid, so unused slots are
  never returned and a failed fetch keeps them. Sourabh's evening: 25 slots gone after 5 articles,
  17 concepts added.
- With no slots, phase 2 skips growth; an article outside the graph links 0–2 demands; notes are
  drawn only for linked demands; the extension says "Nothing new for you on this page". The stored
  page is reused, so it stays empty even after the daily reset.
- Decision 53 raised the caps (60 per reader, 300 a day). The design faults remain.

## Decisions
1. **Reserve in phase 2, exactly what growth will try.** Growth costs one define call per pick
   (merged or rejected picks still cost), so the fair count is the number of picks. `_grow` computes
   `want = len(pick(demands, paragraphs, GROWTH_PER_ARTICLE))` first, then reserves `want` through a
   reserver the caller passes in, then grows with what was granted. Nothing is reserved before a
   fetch, nothing for a page with no unlinked candidates, and there is nothing to refund afterwards.
   A failed growth run keeps its slots (its calls were billed).
2. **No uid on shared content.** The reserver is a closure built by the route from the caller:
   `quota.growth_reserver(caller, settings) -> Callable[[int], Awaitable[int]]` (or `None` when
   growth is off). `analyse_pending(content_id, reserve=None)` and `ingest_url(url, source,
   reserve=None)` pass it to `_grow`. The pending doc never learns who reserved.
3. **Phase 1 reserves nothing.** The three `reserve_growth` calls in phase 1 and the one in
   `open_media` are removed. `PendingDoc.grow_slots` stays readable for docs created before the
   deploy (a pending doc with `grow_slots > 0` uses those and reserves nothing more); new docs
   write 0.
4. **Who reserves.** POST /v1/content (URL path, runs both phases), extension text when not
   deferred, POST /v1/content/{id}/analyse (web "Open here", Read any link, extension deferred,
   media after transcription): the caller's reserver. Scripts (`ingest_corpus`, `ingest_media`),
   held-out ids and corpus sources: none (as today).
5. **Pages that missed growth are marked.** `ContentDoc.grow_pending: bool | None = None`. Phase 2
   sets it to `granted < want` (true when the caps cut growth short, false otherwise; false when
   growth is off). Growth that ran and failed sets false (no retry loop on a failing page).
6. **Old pages.** `grow_pending is None` (stored before this deploy) counts as pending only for a
   `NOT_CORPUS` source (`user_ingested`, `extension`) with at least one pick and no growth call in
   `llm_calls` (`concept_define`, `link_merge`, `concept_prereqs`). Corpus and fetch-source pages
   never regrow (no surprise model spend on library articles). One pure helper,
   `growth.needs_growth(doc) -> bool`, unit-tested.
7. **Grow on reopen: a separate request, never in the scoring path.** New POST
   `/v1/content/{id}/grow` (access as `…/analyse`, `require_readable` for extension docs):
   - not stored → 404; `needs_growth` false → 200 `{status: "none"}` with no model call;
   - claims the page in one transaction (`grow_pending` → false, `growing_until` now + growth
     timeout + 30 s; another live claim → 202 `{status: "growing"}`);
   - reserves through the caller's reserver; 0 granted → claim released, `grow_pending` true,
     200 `{status: "capped"}`;
   - runs `grow` on the stored demands and paragraphs under `GROWTH_TIMEOUT_S`, merges the
     outcome into the doc's demands (`target_id`, `grown`), appends the calls to `llm_calls`,
     sets `grow_pending = granted < want`, clears `growing_until`, writes the doc, refreshes the
     in-memory graph (`get_refresher().apply`), answers 200 `{status: "grown", linked: n}`;
   - a growth failure clears the claim, sets `grow_pending` false, answers 200 `{status: "none"}`
     (logged; the reader keeps the page as it is).
   The paragraphs and the text are never changed; only demand links are.
8. **Clients.** `GET /v1/content/{id}` adds `grow_pending: bool` (the helper's answer).
   - Web ReaderPage: when ready and `grow_pending`, one POST `…/grow`; on `grown` it reloads the
     annotations once. No new UI beyond a polite status line while it runs ("Adding this page's
     ideas to your map…"), in the existing notice. Main bundle ≤ 150 KB (149.61 now: the change
     must stay ≤ 0.3 KB; measured before and after).
   - Extension 0.8.1: after analysis, if `grow_pending`, toast "Adding this page's ideas to your
     map…", POST `…/grow`, then reload annotations. Final toast: notes → "Notes are ready: N on
     this page."; 0 notes and `capped` → "This page's ideas aren't on your map yet. Gloss adds new
     ones a few pages at a time; open it again tomorrow."; 0 notes otherwise → "Nothing new for you
     on this page." New release zip `extension-v0.8.1`.
9. **Caps unchanged** (60 per reader, 300 a day in production). The Medium row's "failed fetches
   use slots" is fixed by 1 and 3; anonymous traffic stays bounded by its 30 new URLs a day.

## Tests (written first)
- `growth.needs_growth`: explicit true/false; old page by source, picks and growth calls.
- Service: phase 1 reserves nothing (all three routes and `open_media`); phase 2 reserves exactly
  the picks, capped at 5; a page with no candidates reserves nothing; partial grant → `grow_pending`
  true; growth error keeps slots and sets false; an old pending doc with `grow_slots` uses them and
  doesn't reserve; scripts reserve nothing.
- Route `…/grow`: none (no call), capped (no call, pending stays), grown (links merged, calls
  appended, text unchanged, pending recomputed), busy claim 202, failure → none and claim cleared,
  extension doc unreadable → 404, a corpus page never grows.
- Growth counters (`users/{uid}/growth_counts`, `ops/growth/days`) equal the picks tried.
- Web: ReaderPage calls `…/grow` once when `grow_pending`, reloads annotations on `grown`, never
  otherwise. Extension: the three toasts.

## Risks
- A reopen now costs growth calls the first time per page (bounded by the reader's slots and the
  $8 guard). `needs_growth` excludes corpus pages so the library never regrows.
- Two instances: the claim transaction keeps one grower per page.
