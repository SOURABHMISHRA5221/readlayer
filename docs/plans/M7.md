# M7 plan: consent, onboarding, calibration, reading profile page, knowledge map, edit-by-prompt

Status: **APPROVED** by plan-reviewer (round 2; 11 round-1 items and 5 nits applied).
**C1 decided by Sourabh (2026-10-10): variant B, session-scoped.** Demo readers can edit by
prompt, but only for their own demo session: edits change that session's copy of the persona
(`users/{uid}/demo_graphs/{persona}` and the session's settings), never the persona template or
anyone else, and the persona is back to its original on the next demo session (End demo deletes
the session). A "Reset persona" button returns it to the original within the session.

## Context

Signed-in (Google) readers start neutral today (θ = 0, no edges, STATUS §4) because there is no
onboarding, and the reading-profile API from M3 (GET /v1/me/profile, GET/PATCH /v1/me/graph,
PATCH /v1/me/settings, export, delete) has no UI. M7 gives a Google reader a consent screen and a
90-second onboarding with calibration so their first article is already personal, and gives every
reader (Google and demo) a profile page: summary, ability vs interest, a per-domain knowledge map
(Cytoscape + dagre, with a keyboard list view), this week's changes, analogy domains, data
controls, and "Edit profile with a prompt" (DESIGN §15.3). The judges' demo uses the profile page
to show "the graph learning" (BUILD_PLAN M9 video).

Built on: M3 profile/graph/settings API, M4 scorer and demo graphs, M5/M6 explanations
(`explanation_style` is already an input of the Background prompt and its cache key, so "keep
explanations short" changes the next card with no further explain work).

Date: Oct 12–13 in the schedule; starting Oct 10 (ahead). Code freeze Oct 16.

## A. Consent, onboarding, calibration (API)

1. **POST /v1/me/consent** (new route, added to DESIGN §8) `{version}` → stores
   `consent: {version, at}` on `users/{uid}`
   (Google readers; anonymous readers never see it: demo mode is covered by the sign-in page's
   "Ending the demo deletes what it recorded"). Consent text version `consent-v1` lives in the
   web app; the API only records which version was accepted.
2. **POST /v1/onboarding** (Google readers only; 403 for anonymous; 409 without consent):
   `{field, interests[], comfort{domain: new|some|comfortable|expert}, thinks_in[≤3],
   liked_content_ids[≤3]}`.
   - `field`: one of a fixed list (software, finance, commerce, law, science, medicine, design,
     teaching, other). It suggests a default THINKS_IN in the UI (software → software, law → law,
     science → science, medicine → medicine, design → design, teaching → teaching); the reader's
     explicit THINKS_IN choice is what is stored.
   - θ per domain from comfort: new −1.5, some −0.5, comfortable 0.5, expert 1.5 (the same
     targets as §15.3 `set_domain_level`, so the two paths agree).
   - interest per domain: 1.0 for chosen interests, 0.3 otherwise.
   - **Liked articles are chosen from the library, not pasted URLs** (deviation from DESIGN §8's
     "optional liked URLs"): no ingest, no LLM cost, no SSRF surface during sign-up. Each liked
     article adds `liked_article_mention` evidence (+0.2, DESIGN §4) to its linked concepts with
     salience ≥ 0.7, at most 15 per article.
   - Writes `users/{uid}` (field, thinks_in, onboarding answers, `onboarding_step: calibration`)
     and `users/{uid}/domains/{d}`; all already covered by export/delete
     (`USER_SUBCOLLECTIONS` / user doc). Idempotent: a second POST overwrites the answers and θ.
3. **GET /v1/calibration/next** → `{item: {concept_id, label, definition?: null, domain}, asked,
   total: 8}` or `{done: true}`.
   - Pool per interest domain: the 150 highest-`doc_freq` concepts (from `concepts.json`), so
     every item is a term a news reader meets.
   - Pick: round-robin over the reader's interest domains (all four if none chosen); within the
     domain the concept with `b` closest to the current θ, not yet asked. Deterministic (ties by
     concept id) so tests are stable.
   - `asked` is stored as `users/{uid}.calibration = {asked: [ids], answers: n}` (≤ 8 ids:
     bounded).
4. **POST /v1/calibration/answer** `{concept_id, answer: explain|heard|none}`:
   - must be the item `next` would return (or one already asked: re-answer replaces nothing,
     returns 409) so a client can't spray answers;
   - evidence `calibration_answer`: explain +3.0 and none −3.0 are DESIGN §4's ±3.0;
     **heard −1.5 is a new rule** (knows the word, not the idea), written into DESIGN §4 at Ship;
   - Elo θ update with K = 0.3 (onboarding) and outcome explain 1, none 0, **heard 0.5 (new
     rule, DESIGN §4 at Ship)**;
   - after the 8th answer `onboarding_done = true`. A **Skip** button posts
     `POST /v1/calibration/skip` which sets `onboarding_done = true` with whatever was answered.
   - Pure logic (pool, pick, evidence, θ) in `app/reader/onboarding.py`, no I/O; the route and
     repo method do one transaction.
5. **GET /v1/me/profile** gains `onboarding: {consented, done, step}` so the web app can gate.
   Anonymous readers report `done: true` (personas).
6. **Nothing is recorded for a Google reader before consent** (DESIGN §11.4; the web gate alone
   isn't enough, and M8's extension skips it): for a Google caller with no `consent`,
   POST /v1/events returns `applied: false` and writes nothing, and the annotations path skips
   its weekly and page-view writes; POST /v1/recs/events writes no `rec_signals`. Corrections
   and settings need consent too (403). Export and DELETE /v1/me stay open without consent, so a
   reader can always leave. Tests for each.

## B. Profile API additions

1. Subgraph nodes gain `recent: [{type, at}]` (last 3 evidence items, newest first) so the node
   card needs no extra request. Types are mapped to plain language in the web app ("You opened an
   explanation · 3 Oct"). Payload stays ≤ 60 nodes × 3 items.
2. GET /v1/me/profile `domains[].interest` already exists; onboarding now fills it.
3. **Demo readers' frames:** GET /v1/me/profile returns the persona's frame
   (`PERSONA_THINKS_IN`, the one explanations use) in `thinks_in` and in the summary text for a
   demo reader, not `user.thinks_in`. The web shows it read-only ("The trader thinks in
   cricket"). Tests for both. The weekly trend is per uid, so a demo session's trend mixes
   personas: noted on the page ("this demo session") and in STATUS §5.
4. No change to PATCH /v1/me/graph (corrections) or PATCH /v1/me/settings (THINKS_IN ≤ 3, style,
   density, pause) beyond the consent rule in A6: both exist and are tested.

## C. Edit profile with a prompt (API, DESIGN §15.3)

1. **Who — Sourabh decides before C starts** (judges on the live site are anonymous, so a
   Google-only box is invisible to them; decision 27 says nothing is dropped without asking):
   - **Variant A, Google readers only:** demo readers see the box disabled with "Sign in with
     Google to describe yourself in words".
   - **Variant B, also demo readers (CHOSEN, session-scoped):** edits apply to
     `demo_graphs/{persona}` of this session only (never `persona_templates`) through the same
     pure apply/undo, under the existing 800 KB demo-doc guard; 3 parses per anonymous uid per
     day and 30 per day shared across all anonymous readers (`ops/profile_edit/days/{day}`, the
     DESIGN §11.5 anonymous pattern); the edit docs live in `users/{uid}/profile_edits` with a
     `persona` field (covered by export/delete); End demo deletes them. Undo on a demo graph
     skips (never recreates) an edge the 800 KB guard dropped after apply (test).
     - Session-only frames: a demo edit's `set_thinks_in` is stored on the session's persona
       copy (`demo_graphs/{persona}.thinks_in`) and used by explanations for that session;
       style and density go on the session's `users/{uid}` as for any reader.
     - **Reset persona:** POST /v1/me/demo/reset `{persona}` deletes this session's
       `demo_graphs/{persona}` (reads fall back to the template) and its pending/applied demo
       edits for that persona; test that the template is untouched and the next load equals the
       template's.
2. **Parse:** POST /v1/me/profile/edits `{text ≤ 500 chars}`.
   - Server-side redaction first (`app/privacy/redact.py`: emails, phone numbers, Luhn-valid
     digit runs, Aadhaar/PAN-like patterns → placeholders), the same module M8's Presidio
     backstop will wrap.
   - `llm.run("profile_edit", ProfileEditOps, vars)` on a new route `profile_edit:
     Route("model_fast", "model_fallback")`, prompt `app/prompts/profile_edit.md`
     (`profile-edit-v1`). Vars: the redacted text inside content delimiters, the domain list, the
     allowed THINKS_IN list. No uid, no history, no concept ids (a test pins the key set).
   - Output: Pydantic discriminated union of the six ops in §15.3, `extra="forbid"`, ≤ 20 ops,
     ≤ 30 names per op. Anything off-schema → 422 "Couldn't understand that, try rephrasing";
     nothing partially applied.
   - **Name cap:** at most **30 distinct concept names per edit across all ops**, checked before
     any linking; over it → 422 "Too many concepts in one edit".
   - **Resolve** names through the graph linker: new `app/graph/resolve.py` wraps the existing
     linker steps for bare names: exact aliases first (free), then embedding candidates and at
     most **3 `link_confirm` batches** (≤ 30 names) per parse; the model never supplies ids.
     Unresolved names are returned as `unresolved` in the response and dropped.
   - Preview: θ before → after per domain, concepts affected per direction (counts + list),
     settings before → after. Stored as `users/{uid}/profile_edits/{edit_id}` with
     `status: pending`, `expires_at` (+1 h), op kinds and values and the **resolved concept ids
     only**: never the raw text and never reader-typed strings (unresolved names are returned in
     the response only, never stored or logged). Expired pending edits are deleted on the next
     parse or list call.
   - Logs: `uid_hash`, op counts, unresolved count, cost. Never the text or any typed name.
3. **Apply:** POST /v1/me/profile/edits/{id}/apply (pending, unexpired, own edit):
   - mark_concepts: evidence `profile_edit_concept` ±3.0 per concept;
   - set_domain_level: θ ← θ + 0.5·(target − θ); ±2.0 `profile_edit_domain` evidence on the
     domain's 10 highest-`doc_freq` concepts (+ where b ≤ target, − where b > target);
   - style, density, THINKS_IN, pause: set on `users/{uid}`;
   - records the exact deltas (Δα/Δβ per concept, Δθ per domain, previous settings) on the edit
     doc (`status: applied`) and writes one `profile_edit` event (TTL like all events). Applies
     even while learning is paused (the reader asked for it, DESIGN §15.1).
   - One transaction over at most 30 named concepts + 4 domains × 10 core concepts = 70 concept
     docs; the edit doc's deltas (≤ 70 × ~80 B ≈ 6 KB) stay far below 1 MiB.
4. **Undo:** POST /v1/me/profile/edits/{id}/undo subtracts the recorded deltas (α, β floored at the
   prior pseudo-counts), reverts Δθ, restores previous settings unless changed since; evidence
   added after the edit stays. `status: undone`. GET /v1/me/profile/edits lists the last 10.
5. **Limits:** 10 parse requests per user per day (`profile_edit_counts/{day}`, a new
   `USER_SUBCOLLECTIONS` entry, so export and delete cover it), refunded only when no model call
   was made. Per-minute general limit as usual.
6. **Evals** (`evals/cases/profile_edit.yaml`, committed before the first model run): 6 phrasings
   with expected ops (incl. the acceptance sentence) and 4 adversarial texts (instructions to
   invent ids, to call another tool, to set an op outside the whitelist, a prompt-injection
   phrase); `uv run python -m evals.run --suite profile_edit` reports pass/fail and cost.
   Target: 6/6 expected op sets (names may differ in case), 4/4 adversarial produce only
   whitelisted ops and no invented ids. Any prompt change bumps the version and is reported
   before and after in `evals/report.md` (a profile-edit section) and `evals/changelog.md`.
   Cases are never edited or dropped to make a number pass (decision 26).

## D. Web: gate, consent, onboarding, calibration

1. Router gains `/welcome` (consent → onboarding → calibration) and `/profile`.
2. Gate: a Google reader whose profile says `onboarding.done === false` is sent to `/welcome`
   from any route; anonymous readers never are. After Delete my data the user is signed out;
   signing in again starts at consent (acceptance).
3. Consent (`consent-v1`): what we collect (reading signals, onboarding answers, settings), why
   (to choose and phrase notes for you), what we never do (send your email or history to an AI
   model, sell data), export / delete links; Continue / Sign out.
4. Onboarding steps (one screen each, progress dots, Back): field → interests (multi-select
   domains) → comfort per chosen domain (4-step segmented control) → analogy frames (≤ 3,
   preselected from field) → optional liked articles (search the library, pick ≤ 3) → calibration
   (8 taps: concept label, "I could explain it" / "I've heard of it" / "New to me", Skip) → done
   → library. Target: 90 s for a reader who skips liked articles.
5. All controls are native buttons/inputs with labels; ≥ 44 px targets; keyboard order matches
   visual order; focus moves to each step's heading on step change.

## E. Web: profile page

0. `WelcomePage` and `ProfilePage` load with `React.lazy` (route chunks), so the main bundle
   (128 KB gzip today, budget 150 KB) doesn't grow with M7.
1. Sections per DESIGN §15.1: summary card, ability vs interest bars (numbers as text, fixed
   −2..2 scale for ability), knowledge map per domain, this week (moved up + trend sparkline with
   a text table fallback), analogy domains (chips, ≤ 3, PATCH settings), explanation length and
   density (segmented), data controls (Export, Delete, Pause with banner while paused).
2. **Knowledge map:** `cytoscape` + `cytoscape-dagre` (pinned versions, in `dependencies`),
   bundled by Vite into a chunk loaded with `import()` only when the map section opens. Report
   the main bundle and the route and map chunk sizes. Layered top-down layout (foundations on top). Node fill
   by band plus a shape/label cue (unaware ○, heard of ◔, understands ◑, can explain ●) so colour
   isn't the only signal. Search box → GET /v1/me/graph?domain=X&q=term.
3. **List view** of the same subgraph grouped by depth: the default below 640 px and a toggle
   above it; each concept is a button opening the node card.
4. **Node card** (dialog, focus trap, Escape returns focus): band, last 3 evidence items in plain
   language, "I know this" / "I don't" → PATCH /v1/me/graph/{id}, then the map/list refresh.
5. Demo readers see their persona's profile (summary, map, corrections apply to the persona's
   demo graph through the existing persona-scoped endpoints); Export/Delete are replaced by
   "End demo" as today.

## F. Web: edit box

Textarea "Describe yourself as a reader", the AI notice line, Preview → diff (domains θ
before → after, concepts known/unknown counts with expandable lists, settings changes,
"Couldn't find: …"), Apply / Discard, list of applied edits with Undo. For demo readers it follows
the C1 variant: disabled with the sign-in prompt (A), or enabled against the persona's graph (B).

## G. Local end-to-end harness (no production writes)

`make dev-emulator`: Firestore + Auth emulators (project `demo-readlayer`), a seed script that
copies 5 library articles and the 3 persona templates **read-only from production** into the
emulator, the API with `FIRESTORE_EMULATOR_HOST` / `FIREBASE_AUTH_EMULATOR_HOST`, and the web app
with `VITE_USE_EMULATORS=1` (connects Auth to the emulator; never set in a Hosting build: a build
check fails if it is). The Auth emulator's fake Google account picker lets headless Chrome sign in
as two different "Google" readers (software engineer, commerce student) without creating real
accounts. Used for acceptance 1–4 and the design critique.

Safety rails:
- **Budget guard stays real.** The spend ledger lives in Firestore, so under the emulator it would
  start at $0. The seed script copies today's production `ops/spend/days/{date}` into the
  emulator, and the harness sets `LLM_DAILY_BUDGET_USD = min(1, 8 − today's production spend)`.
  The harness ledger total is reported in STATUS §7 (and added to the day's production figure).
- **Emulator settings never reach a deployed API.** `Settings` validation refuses to start when
  `FIREBASE_AUTH_EMULATOR_HOST` or `FIRESTORE_EMULATOR_HOST` is set and `K_SERVICE` is set or
  `ENV=prod` (the `DEV_AUTH_BYPASS` pattern); test included.
- **The seed script can't write to production.** It writes only through a client built
  explicitly for project `demo-readlayer` with the emulator host asserted, reads production
  through a separate client created with no emulator env, and refuses to run if both point at
  the same target.

## Data rights, privacy, cost

- New user data: `users/{uid}` fields (consent, field, onboarding answers, calibration),
  `profile_edits` (already listed; ops, values and resolved ids only), `profile_edit_counts`
  (new, added to `USER_SUBCOLLECTIONS`).
  The existing test that fails on any write under `users/{uid}` outside that list guards it.
  Export/delete tests extended to the new fields.
- To an LLM: only the redacted profile-edit text plus fixed lists (profile_edit), and concept
  names (link_confirm). Never uid, email, history or ids.
- Cost per parse is bounded: ≤ 30 names, aliases first, ≤ 3 `link_confirm` batches → at most
  ≈ $0.0005 + 3 × $0.007 ≈ $0.02; 10 parses/day per Google reader ≈ $0.20 worst case.
  Anonymous readers: nothing new that costs money under variant A; under variant B, 3 parses/uid
  and 30/day shared (≈ $0.60/day worst case for all anonymous readers together).
- Scoring path unchanged: no LLM on annotations; `reader/onboarding.py` is pure.
