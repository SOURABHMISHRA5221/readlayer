# Decision 50: a For you feed worth reading (Sourabh, 2026-10-11)

## Context

After Redo setup worked (decision 48, live), Sourabh: "the Feed is not up to mark". Two
problems, his words:
1. "After updating my preference I should get a refresh feed option."
2. "News articles fetched are not worth reading for me; got very local sources news. News/articles
   should be of top orgs that give worth to read." (Harness and live: advertiser-tribune.com,
   swampscotttides.org, roanoke.com, a "Politics" tag page from economist.com.)

He asked whether TinyFish (a browser agent) could search better. Answer given: not for a feed
(slow, per-task cost, non-deterministic); instead take news straight from top organisations'
section feeds. His choices: **outlet mix 40% global + 60% the reader's own country**; a
**scheduled job twice a day**, "as long as cost is not killing".

Order (decision 49, Sourabh 2026-10-11): this (decision 50) → M8-local (extension) → Wide layout.

## A. Outlet registry (`app/recs/outlets.py`, data + pure helpers)

- `Outlet {id, name, domain, region: "global" | "IN" | "GB" | "US", sections: {topic: [feed_url]}}`.
  Launch set: global = BBC, The Guardian, NPR; IN = The Hindu, Indian Express, Mint, Economic
  Times; GB's own outlets = BBC, The Guardian; US's own = NPR. A reader in GB/US gets their
  country's outlets as "local" and the other global ones as "global"; any other country, or none
  set, gets global outlets only.
- Every one of the 14 topics maps to ≥ 1 global section and ≥ 1 IN section where the outlet has
  one (the table is in the module; a test checks coverage and that every URL is https on the
  outlet's own domain). Topics an outlet doesn't cover fall back to its closest section
  (e.g. policy → national/politics) or to the search fallback (§D).
- `scripts/check_outlets.py` (local, no LLM): for every feed, items parsed and 3 recent articles
  fetched + extracted; an outlet is `readable` when ≥ 2 of 3 reach 400 words. Output committed
  as `docs/evidence/d50/outlets.txt`; unreadable outlets are dropped from the launch set.

## B. Twice-daily collection job

- `POST /v1/internal/feeds/collect`: callable only with a Google OIDC token for the scheduler's
  service account (audience = the service URL; verified with `google.oauth2.id_token`); 403
  otherwise; never reachable with a Firebase token. Runs inside the request (Cloud Run allows
  300 s): fetch every registry feed through `safe_fetch` (XML content types, size cap), parse
  with `feedparser` (already a dependency), keep items ≤ 3 days old, English, article-shaped,
  dedupe by URL, write one entry per (outlet, topic, run) to `rec_cache` under
  `outlets:<topic>:<region>` with the run time. No reader data anywhere: the job doesn't know
  any reader. No LLM, no Tavily.
- Cloud Scheduler: two jobs, 06:00 and 18:00 IST (`make setup-feed-job`, needs Sourabh's yes:
  creates a service account + `roles/run.invoker` + 2 scheduler jobs; IAM changes ask first).
  If a run fails, the previous run's entries keep serving; a run older than 36 h is logged.
- Cost (stated to Sourabh): Scheduler's free tier covers 3 jobs per billing account (we'd use
  2); the job is ≈ 50 feed fetches + parsing, well inside Cloud Run's free CPU; ≈ 30 Firestore
  writes per run (free tier 20,000/day). Expected **$0/month**; Tavily calls for articles drop.
- Article readability is **not** checked per item in the job (≈ 300 fetches a run); the registry
  only holds outlets measured readable (§A), and the reader view's existing two-phase "Open here"
  still handles a rare short page.

## C. The feed reads outlets first, 60/40

- `GET /v1/feed` article candidates for a signed-in reader come from the latest collected
  outlet entries for their topics: "local" = their country's outlets, "global" = the others.
  Ranking per topic unchanged (interest × readiness × goal boost × freshness × format affinity),
  plus a mix rule in `select`: over the article slots, **60% local / 40% global** (± 1 item),
  topics interleaved as today. No country (or unsupported) → global only. Video and podcast
  formats unchanged (YouTube / Tavily podcast).
- Demo personas: snapshots re-seeded from the outlet entries (`seed_demo_feed` reads the registry
  instead of searching; persona country IN). Production write listed in §Production writes.
- Onboarding screen 2 (`discover`) uses the same outlet entries for topics; concept searches
  (resolved free-text concepts) stay on Tavily, restricted per §D.

## D. Search fallback only on top outlets

- When a topic has fewer than 3 outlet articles for the reader's mix (or for concept searches),
  Tavily article searches pass `include_domains` = the registry's readable domains (+
  reuters.com, apnews.com as global wires). Never `exclude_domains` (STATUS §5: it emptied
  results). Measured on the harness before relying on it: per topic, results with and without
  `include_domains`; if `include_domains` returns < 2 articles for most topics, the fallback is
  dropped and the topic shows outlet articles only (recorded).

## E. Country

- `UserProfile.country: "IN" | "GB" | "US" | "other" | None`. Screen 1 of onboarding and the
  profile's Preferences get "Where do you read from?" (India, United Kingdom, United States,
  Somewhere else), **prefilled from the browser's locale region** (`navigator.language`, e.g.
  en-IN → India) and stored only when the reader saves. Sourabh's account: set through Redo
  setup or Preferences. Export/delete via the user doc; `/privacy` lists it ("the country you
  chose, to mix in news from there").
- Never sent anywhere: the job doesn't know readers; the feed uses it only to pick outlets.

## F. Refresh

- The For you tab refetches automatically when the reader's preferences change: after Redo
  setup's Start reading, a profile edit Apply/Undo, a goal saved or removed, or a country
  change (one `rl:feed-stale` window event). A **Refresh** button on For you refetches on
  demand; with the outlet entries already collected it costs no search. While new topics have
  no entries yet (a topic the job hasn't covered), the existing "pending" line shows.

## Privacy and cost (summary)

The job sends no reader data (it has none); feeds and outlet fetches carry no query at all.
Tavily use falls (fallback only, restricted to top outlets). New stored datum: `country`
(reader-chosen). Spend: $0 expected; no LLM in any new path.

## Round 1 (plan-reviewer REVISE, 13 items; all applied, these override the sections above)

1. **Internal endpoint auth.** `POST /v1/internal/feeds/collect` verifies a Google ID token with
   `google.oauth2.id_token.verify_oauth2_token` (in a thread, cached `requests` session for
   certs) and requires: `iss` = accounts.google.com, `email_verified`, `email` ==
   `FEED_JOB_SA_EMAIL`, `aud` == `FEED_JOB_AUDIENCE` (configured, not derived from the request:
   Cloud Run answers on two URLs). Either setting missing → 403 (fail closed). Tests for each
   rule. No `roles/run.invoker` binding (the service is allUsers-invokable; it would add nothing).
   `make setup-feed-job`: enable `cloudscheduler.googleapis.com`, create the service account,
   2 jobs with OIDC token (SA, audience), `--attempt-deadline=300s`, `--max-retry-attempts=1`.
2. **Feed parsing safety.** Every fetch goes through `safe_fetch` with the feed content types
   already in `scripts/collect_corpus.py` (3 MiB cap); `feedparser.parse` only ever receives
   those bytes, never a URL (test: a monkeypatched `feedparser.parse` asserts bytes); parsing in
   a thread. collect_corpus's parse / canonical-URL / path-deny helpers move to
   `app/recs/outlet_feed.py` and the script imports them. Item links accepted only on the
   outlet's article hosts. Descriptions: tags stripped, then unescaped and clipped.
3. **Registry hosts.** `Outlet.feed_hosts` and `Outlet.article_hosts` separately (BBC: feeds on
   feeds.bbci.co.uk, articles on bbc.co.uk / bbc.com); tests check each list.
4. **Cache layout.** One doc per topic: `rec_cache/outlets:<topic>` = `{outlet_id: {items: [≤ 20
   newest], fetched_at}}` (≤ ~140 items, ~100 KB). Each run merges per outlet (a failing outlet
   keeps its previous list). Local/global is derived at read time from the registry and the
   reader's country. 14 writes per run; ≤ 6 reads per feed request. Read through a new
   `OutletStore.read(topics)`, never through `cached_entry` / `fetch_feed` (no staleness
   refetch, never Tavily).
5. **No unrestricted cache after deploy.** The restricted fallback uses a new key stem
   (`feedx:<topic>:<day>` for topic fallbacks, `feedx:c:<concept>:<day>` for onboarding concept
   searches); the yesterday fallback reads the same new stem, so old `feed:` entries (with the
   small local papers) are never served again.
6. **One fallback query for everyone.** `include_domains` = the full registry article hosts +
   reuters.com + apnews.com, constant, never filtered by country. Test: two readers differing
   only in country produce byte-identical Tavily request bodies and cache keys (replaces the
   collect-path property test).
7. **The 60/40 mix.** Applied across all article picks of the feed (before the 24-item cut, after
   per-topic ranking): each item tagged local/global from its host via the registry (Reuters,
   AP = global); target local = round(0.6 × article slots); a short side is backfilled from the
   other side before any Tavily fallback; the shortfall is reported in logs (counts only).
   Videos/podcasts are outside the mix. Test: short local supply backfilled; ±1 holds when
   supply allows.
8. **Outlet items skip the topic-word filter** (the section is the topic); concept extraction
   still runs for readiness. Live blogs, video and audio pages are dropped (URL path segments
   `live`, `video(s)`, `audio`, `av`, `podcasts`; BBC `/av/`, Guardian `/live/`); fixture tests.
9. **URLs canonicalised before dedupe** (collect_corpus's canonical helper: tracking params and
   fragments dropped); fixture test with one story in two sections.
10. **Demo snapshots.** `seed_demo_feed` reads the outlet docs (production entries exist only after
    a job run) and keeps its local ≥ 400-word check. Personas' country is a constant
    `PERSONA_COUNTRY` in `app/recs/feed.py`: **global-only until Sourabh decides** (India would
    make the judges' demo feed 60% Indian outlets). Deploy order: API → scheduler setup (his yes)
    → one manual run → `seed_demo_feed --dry-run` → real seed → web. Replaces STATUS §5's
    thin-topic item and the Oct 16 re-seed step.
11. **Dry runs and counts.** `scripts/collect_outlets.py --dry-run` (local, prints per-outlet item
    counts, writes nothing) before the first real run; the endpoint has no dry-run. Production
    writes: `rec_cache/outlets:*` ≤ 14 docs overwritten per run; `persona_feeds/*` 3 docs; 1
    `country` field on Sourabh's user doc (his own action). Before the first run the feed
    degrades to the restricted fallback or the pending line, never an error (test).
12. **Country.** Written by `POST /v1/onboarding` (screen 1, field `country`) and `PATCH
    /v1/me/settings`; validated `IN | GB | US | other`; anonymous readers neither see nor store it.
    Readers without one (every existing reader, Sourabh included) get global outlets only, and For
    you shows one line "Add your country for news from where you live" linking to Preferences.
    Tests: export contains it, delete removes it; it never reaches an LLM prompt or a search
    request.
13. **Cut order inside the milestone.** Checkpoint end of Oct 12 IST: if not harness-accepted, cut
    in this order and tell Sourabh: (1) GB/US local mixes (IN + global only); (2) the Tavily
    fallback (outlet articles only); (3) the country field in Preferences (onboarding / Redo
    setup only).
