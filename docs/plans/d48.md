## Shared: one topic matcher (`app/reader/onboarding_text.py`)

`match_topic(graph, phrase) -> TopicMatch | None` packages the onboarding order for a single
redacted phrase: whole-phrase alias → `word_topic` (words and 2-word chunks against aliases and
concept labels, no model call) → nearest topic scope line by embedding (one phrase per request,
cosine ≥ `ONBOARDING_TOPIC_THRESHOLD`). Returns `{topic, via, words}` where `words` are the
kept words/chunks (for the goal's concept pick). The onboarding route keeps its current order
(exact concept → alias → words → `resolve_names` → embedding) and calls the same helpers; no
behaviour change there (existing tests).

## 1a. Learning goal on a topic (`app/me/goals.py`, `app/reader/goals.py`)

Resolution order for "understand X" (text redacted, leading verb stripped, as today):
1. exact concept label/alias → concept goal (as today, no model call);
2. `resolve_names` (embedding candidates + `link_confirm`, this one phrase only) → concept goal
   (as today);
3. else `match_topic` → **topic goal**; else 422 "couldn't find" (as today).

Topic goal targets (pure, `goals.topic_targets(graph, topic, words, limit=10)`): concepts of that
domain whose label or an alias contains one of the phrase's kept words (stop/generic/country words
already removed; the topic's own label word, e.g. "politics", doesn't count as a match), ordered
by `doc_freq` desc then id; then filled to 10 with the domain's most frequent concepts
(`doc_freq` desc). Concepts with `doc_freq` 0 only if the domain has fewer than 10 met in the
corpus. Progress: `learning_progress` over those ids, as today.

**Preview, then save** (no double resolve, nothing typed is stored):
- `POST /v1/me/goals/preview {type: learning, text}` → `{kind: concept|topic, topic, label,
  targets: [{concept_id, label}], matched_words: n}`; counts against `GOAL_RESOLVE_DAILY_CAP`
  (the resolve happens here); nothing written. Errors as today (422 not found, 429 cap).
- `POST /v1/me/goals {type: learning_resolved, kind, topic?, concept_id?, target_ids}` saves a
  previewed goal: the server re-validates every id exists in the graph (topic goal: every id is
  in `topic`'s domain, ≤ 10; concept goal: `target_ids` must equal `goals.targets(graph,
  concept_id)`), recomputes labels from the graph, no model call, no cap charge. The old
  `{type: learning, text}` create stays for compatibility (one-step, as today).
- Stored label: concept goals as today; topic goals `Politics` (taxonomy label) with `kind:
  "topic"`. **The phrase is never stored** (DESIGN §18 rule): the preview line "Goal: understand
  Politics (Indian politics) · 10 ideas" uses the reader's own text from React state; the saved
  goal reads "Understand Politics · 10 ideas".
- Web (`ProfilePage` goals form): Add → preview line with "Save goal" and "Cancel"; the text box
  keeps its value until saved or cancelled; React state only.

## 1b. Describe yourself: `set_interest` (`app/reader/profile_edit.py`, prompt v6)

- New op `SetInterest {op: "set_interest", topic: Name (≤ 80), direction: "more" | "less"}`. The
  model copies the reader's words for the subject ("Indian politics"), never a domain id. Flat
  schema gains `topic: str = ""` and `direction: Literal["", "more", "less"]`.
- Prompt `profile-edit-v6`: one new line for the op ("I want to read more about X" / "less
  cricket, please" → `set_interest`); "learn about X" counts as `more`. Op count and the other
  rules unchanged.
- Server resolves each `topic` phrase alone through `match_topic` (redacted again; one phrase per
  embed request). Unresolved → the op is dropped and reported in the preview ("Didn't recognise:
  …"), as unresolved names are today. Resolved → `{domain, direction}`.
- Apply: `more` sets the domain's interest to `max(current, 1.0)` (a chosen topic), `less` to
  `min(current, 0.3)` (out of the feed's topics, which need ≥ 0.5). The edit records the previous
  interest per domain; Undo restores it. Preview line: "More Politics in your feed" / "Less Sports
  in your feed".
- Stored: domain + direction + previous value only; never the phrase.
- Evals: `evals/cases/profile_edit.yaml` gains 4 cases (P11–P14: "I want to learn about Indian
  politics", "less cricket please", a mixed one with a level and an interest, and one that must not
  produce `set_interest`: "I'm a cricket fan who works in finance") committed **before** the v6
  run; the suite runs once before (v5, existing cases) is already recorded, once after (v6, all
  cases). ≈ 14 short calls, < $0.02.

## 2. Redo setup

API (`app/me/onboarding.py`, `onboarding_flow.py`, `reader_repo.py`, `router.py`):
- `UserProfile.onboarding_redo: Literal["about", "discover"] | None` (export/delete via the user
  doc).
- `POST /v1/onboarding/redo` (consented Google readers, onboarding done): clears the offered,
  answered and pick lists and sets `onboarding_redo = "about"`. `onboarding_done` **stays true**,
  so the app never gates the reader; they can leave at any time and nothing is lost.
- `POST /v1/onboarding` while redoing: same writes as the first onboarding (field, interests =
  chosen 1.0 / others 0.3 + picks, frame; θ untouched) but **does not** set `onboarding_done =
  false` and does not reset calibration progress; sets `onboarding_redo = "discover"`.
- discover / pick / know: allowed when `onboarding_done` is false **or** `onboarding_redo` is set
  (today: refused once done). Know answers are the same evidence and Elo step; an existing edge is
  updated, not replaced.
- `POST /v1/onboarding/finish`: clears the lists and `onboarding_redo`.
- Profile `onboarding` block adds `redo` and `consent_version`; `step` is unchanged (`done`).
- Caps unchanged (resolve 5, discover 3 per day): a redo shares them.

Web:
- Profile "Your data" area: a "Redo setup" button → `POST /v1/onboarding/redo` → `/welcome`.
- `WelcomePage`: when `redo` is set, screen 1 or 2 per `redo`; fields prefilled from the profile
  (field, ≤ 6 topics); a "Cancel" link back to the profile; Start reading → finish → For you.
- Consent checkbox on screen 1 if not consented **or** `consent_version` isn't the current one
  (`consent-v2`); Sourabh's account has v1, so he will see it once.

## Privacy (unchanged rules, checked by tests)

No raw or redacted phrase is stored, logged or sent to search in any of the three paths; each
phrase reaches a model alone (one embed request, one `link_confirm` call); the goal and edit
documents hold ids, domains, directions and previous values only.
